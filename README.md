# swagger_to_http.py

Converts a Swagger / OpenAPI JSON file into a `.http` file that you can run directly from your editor.

Works with the **VS Code REST Client** extension, **Visual Studio 2022 (17.8+)** and **JetBrains Rider / IntelliJ HTTP Client**.

## Requirements

- Python 3.8+
- No third-party packages (standard library only)

## Usage

```bash
python swagger_to_http.py <swagger.json> [-o OUTPUT_DIR] [--base-url URL]
```

| Argument | Description |
|---|---|
| `input` | Path to the Swagger / OpenAPI **JSON** file (OpenAPI 3.x and Swagger 2.0) |
| `-o`, `--output-dir` | Folder to write the `.http` file to. Default: current folder |
| `--base-url` | Overrides the `@baseUrl` variable. Default: taken from `servers[0].url` (or `host` + `basePath` for Swagger 2.0), falling back to `http://localhost` |

### Example

```bash
python swagger_to_http.py swagger.json -o ./http --base-url https://localhost:5001
```

## Output file name

The file name is built from the `info` block of the spec:

```json
"info": {
  "title": "WebApplication1 API",
  "version": "v1"
}
```

```
{info.title}_{info.version}.http   ->   WebApplication1_API_v1.http
```

Characters that are not letters, digits, `.`, `_` or `-` are replaced with `_`.

## Example output

```http
# WebApplication1 API (version v1)
# Generated by swagger_to_http.py

@baseUrl = http://localhost

### GetWeatherForecast
# @name GetWeatherForecast
GET {{baseUrl}}/WeatherForecast
Accept: application/json
```

## What gets converted

- **One request per operation**, titled by `summary` (or `operationId`, or `METHOD /path`), with `# @name` set from `operationId`.
- **Variables** at the top of the file: `@baseUrl`, plus `@token`, `@basicAuth` or `@apiKey` when the spec uses security, and one variable per path parameter (e.g. `@petId`). Same-named path parameters share one variable.
- **Query parameters**: required ones are added to the URL with example values; optional ones are listed in a `# Optional query parameters:` comment so you can paste in what you need.
- **Headers**: `Accept` (from the 2xx response content types), header parameters, `Content-Type`, and `Authorization` / API-key headers.
- **Request bodies**: JSON, `application/x-www-form-urlencoded` and `multipart/form-data` (file fields use `< ./name.bin`). Example values are generated from the schema: explicit `example`/`default`/`enum` first, then format-aware placeholders (`date`, `uuid`, `email`, ...). `readOnly` properties are skipped, and `$ref`, `allOf`, `oneOf` / `anyOf` (first option) and recursive schemas are handled.
- **Security**: bearer / OAuth2 / OpenID Connect become `Authorization: Bearer {{token}}`, basic becomes `Authorization: Basic {{basicAuth}}`, and API keys go in the header or query as declared. An operation-level `security: []` means no auth.

## Limitations

- JSON specs only (convert YAML to JSON first).
- Only local `$ref` pointers (`#/...`) are resolved.
- Only the first security scheme of an operation is used.
- Cookie parameters and response examples are ignored.
